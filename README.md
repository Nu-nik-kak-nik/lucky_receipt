# Чек на удачу

Промо-акция: покупатель регистрирует чек, модератор проверяет.
Упрощённая версия реального проекта — Django + PostgreSQL + Docker.

## Стек

- Python 3.13 / 3.14
- Django 6.1
- PostgreSQL 16
- Docker, docker compose
- pytest + pytest-django
- django-stubs (для типизации в редакторе)
- Чистый JS на фронте, без сборщиков

## Запуск

### 1. Клонировать и подготовить окружение

```bash
git clone <repo-url> lucky_receipt
cd lucky_receipt
cp .env.example .env
# открыть .env и проверить значения — особенно SECRET_KEY и даты акции
```

### 2. Вариант A — всё в Docker

```bash
sudo docker compose up --build
```

Сайт на http://localhost:8000.

Первого модератора создать так:

```bash
sudo docker compose exec web python manage.py createsuperuser
```

### 2. Вариант B — Django на хосте, только Postgres в Docker (для разработки)

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt

sudo docker compose up -d db

python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

`POSTGRES_HOST=localhost` в `.env` — для этого варианта. В `docker-compose.yml` web-сервис переопределяет его на `db`.

## Переменные окружения

Все настройки — в `.env` (см. `.env.example`).

| Переменная | Назначение |
|---|---|
| `SECRET_KEY` | секретный ключ Django |
| `DEBUG` | 1/0 |
| `ALLOWED_HOSTS` | список хостов через запятую |
| `CSRF_TRUSTED_ORIGINS` | для CSRF при работе за прокси |
| `POSTGRES_DB/USER/PASSWORD/HOST/PORT` | подключение к БД |
| `TIME_ZONE` | таймзона Django |
| `PROMO_TIMEZONE` | таймзона границ акции |
| `PROMO_START_DATE` | начало акции, `YYYY-MM-DD` |
| `PROMO_END_DATE` | конец акции, `YYYY-MM-DD` |
| `PROMO_MIN_AMOUNT` | минимальная сумма чека |

Даты **обязательно** с ведущими нулями: `2026-01-01`, а не `2026-1-1`.

## Что реализовано

### Пользователи
- Стандартный `django.contrib.auth`.
- Регистрация и вход — дефолтные шаблоны Django.
- Модератор — пользователь с `is_staff=True`.
- Отдельный интерфейс модератора не нужен, используется админка.

### Модель чека
`lucky_receipt.models.Receipt`:
- ФН, ФД, ФП, дата и время покупки, сумма;
- статус: `pending` / `accepted` / `rejected`;
- причина отказа;
- пользователь, дата регистрации;
- `UniqueConstraint(fn, fd, fp)` — второй раз тот же чек не пройдёт.

### Регистрация чека
- Форма с серверной валидацией:
  - дата покупки входит в период акции;
  - сумма не меньше `PROMO_MIN_AMOUNT` (по умолчанию 1000 ₽);
  - ФН/ФД/ФП — только цифры, связка уникальна;
  - новый чек всегда получает статус «на проверке».
- Поле `qr_string` — необязательное. Если заполнено, строка вида
  `t=...&s=...&fn=...&i=...&fp=...` парсится:
  - **на клиенте** (JS) — автозаполнение полей;
  - **на сервере** (`lucky_receipt.services.qr_parser`) — как fallback и на случай отключённого JS.

### Личный кабинет
- Список своих чеков: дата покупки, сумма, статус, причина отказа.
- Сортировка от новых к старым.
- Пагинация по 10.
- Кнопка «Зарегистрировать чек».
- Форма отправляется через `fetch`, ответ сервера отображается без перезагрузки.

### Админка
- Список чеков, фильтры по статусу и датам, поиск по ФН/ФД/ФП/пользователю.
- Карточка чека: смена статуса + обязательное поле причины при «Отклонён».
- Массовые действия:
  - «Принять выбранные чеки»;
  - «Удалить выбранные чеки»;
  - «Экспортировать принятые чеки в CSV».

### API
- `GET /api/receipts/` — чеки текущего пользователя в JSON.
- Всегда фильтрует по `request.user`; любые query-параметры игнорируются.

### Инфраструктура
- `docker compose up --build` поднимает Postgres + Django.
- `docker/entrypoint.sh` ждёт готовности БД и накатывает миграции.
- `.env.example` с валидными значениями по умолчанию.
- Настройки логгирования через `LOGGING`.

## Спорные решения

**Повторная регистрация отклонённого чека.** Запрещена. Связка `(fn, fd, fp)` уникальна для всех статусов. Причина: упрощает модель данных, исключает подбор «переотправкой» и соответствует требованию ТЗ «второй раз тот же чек не принимается».

**Границы периода акции.** Включительные: начало — 00:00:00, конец — 23:59:59.999999. Трактуются в `PROMO_TIMEZONE` из `.env`, а не в UTC. Это значит: если пользователь в другом часовом поясе, «последний день акции» определяется по московскому (или указанному в конфиге) времени.

**Часовой пояс в форме.** `datetime-local` отдаёт naive datetime. Приводим к `PROMO_TIMEZONE` в `clean_purchased_at`. В БД всегда лежит aware-время; `USE_TZ=True`.

**Причина отказа.** Обязательна только для статуса «Отклонён». При других статусах очищается автоматически на уровне админ-формы.

**API.** Не принимает параметры сортировки/фильтрации/`user_id`. Если бы понадобилось, добавляли бы явный whitelist. Пока минимализм.

**QR-строка.** Поддерживаются форматы даты:
`%Y%m%dT%H%M%S`, `%Y%m%dT%H%M`, `%Y-%m-%dT%H:%M:%S`, `%Y-%m-%dT%H:%M`.
Если строка не парсится — форма возвращает понятную ошибку у поля `qr_string`, а серверная валидация обязательных полей ловит остальное.

**Клиентская валидация не заменяет серверную.** JS подсвечивает поля и подсказывает, но окончательное решение — за `ReceiptForm.clean()`. Отключение JS не ломает валидацию.

**Копейки.** Сумма — `DecimalField(decimal_places=2)`, на форме шаг стрелок 1 ₽ (`step="1"`), ручной ввод `1500.50` допустим. Минимум — 1000 ₽.

## Что не сделано / план

Обязательная часть ТЗ закрыта. Из бонусов реализовано:

- ✅ строка из QR-кода с автозаполнением формы;
- ✅ выгрузка принятых чеков в CSV из админки;

Не реализовано (осознанно отложено):

- загрузка фото чека с валидацией формата и размера;
- автообновление статуса в личном кабинете без перезагрузки (polling);
- полноценная вёрстка под макет Figma — сейчас структура и цвета близко, но не пиксель-перфект;

Что хотелось бы добавить при наличии времени:
- rate-limit на форму регистрации чека (защита от перебора);
- капча на регистрацию;
- уведомления пользователю при смене статуса его чека.

## Работа с ИИ

При разработке использовался Claude как ассистент. Ниже честный разбор.

**Где помог сильнее всего.** Каркас проекта: настройка `docker-compose` с healthcheck, шаблон `Dockerfile` с ожиданием БД в `entrypoint.sh`, скелет модели `Receipt` с `UniqueConstraint` и индексами. Отдельно — валидация формы: генерация сообщений об ошибках, аккуратная работа с `timezone.make_aware` и границами периода в `PROMO_TIMEZONE`. Плюс шаблон `README` и структура тестов.

**Что выдал неправильно и как это заметил.**
- В `config/urls.py` ИИ оставил `include("receipts.urls")` со старого имени приложения, хотя приложение в проекте называется `lucky_receipt`. Поймал сам по трейсбеку `ModuleNotFoundError`.
- В `_validate_digits` тип аргумента был `str`, хотя `cleaned_data.get()` возвращает `str | None`. Pyright это подсветил.
- Значения по умолчанию в `.env.example` были с пустыми `POSTGRES_*`. Проверил на чистом `cp .env.example .env` — упало на подключении к БД.
- Даты в примере оказались из 2025 года при текущем 2026 — тоже заметил при ручном прогоне.
- Тест `test_export_accepted_csv` проверял `assert "20" not in body`, где `"20"` встречается внутри года `2026`. Ложное срабатывание нашёл, когда прогнал `pytest`.
- QR-поле: серверная логика автозаполнения была, но JS-валидация блокировала отправку раньше, чем запрос уходил на сервер. Обнаружил при ручной проверке в браузере.

**Что бы переписал, будь больше времени.**
- Вынести общую логику валидации реквизитов (`fn`/`fd`/`fp` — только цифры) в отдельные валидаторы Django, чтобы не дублировать между формой и моделью.
- Покрыть `admin.py` более детальными тестами — сейчас проверяются только два сценария.
- Добавить `pytest.mark.django_db` там, где это уместнее, чем `TestCase`.
- Заменить дефолтные шаблоны `login.html`/`register.html` на кастомные, чтобы не выбивались из стиля акции.
