# Чек на удачу

Промо-акция: покупатель регистрирует чек, модератор проверяет.
Упрощённая версия реального проекта — Django + PostgreSQL + Docker.

Коммиты делал по привычки на английском

## Стек

- Python 3.13 / 3.14
- Django 6.1
- PostgreSQL 16
- Docker, docker compose
- pytest + pytest-django
- django-stubs (для типизации в редакторе)
- Pillow (для проверки изображений)
- Чистый JS на фронте, без сборщиков

## Запуск

### 1. Клонировать и подготовить окружение

```bash
git clone https://github.com/Nu-nik-kak-nik/lucky_receipt lucky_receipt
cd lucky_receipt
cp .env.example .env
# открыть .env и проверить значения — особенно SECRET_KEY и даты акции
```

### 2. Вариант A — всё в Docker

```bash
sudo docker compose up --build
```

Сайт на http://localhost:8000.

Первого модератора создать так:

```bash
sudo docker compose exec web python manage.py createsuperuser
```

### 2. Вариант B — Django на хосте, только Postgres в Docker (для разработки)

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt

sudo docker compose up -d db

python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

`POSTGRES_HOST=localhost` в `.env` — для этого варианта. В `docker-compose.yml` web-сервис переопределяет его на `db`.

### Замечание про sudo и Docker

В примерах используется `sudo docker`, потому что пользователь не в группе `docker`. Если вы в группу `docker` — можно выполнять без `sudo`.

## Переменные окружения

Все настройки — в `.env` (см. `.env.example`).

| Переменная | Назначение |
|---|---|
| `SECRET_KEY` | секретный ключ Django |
| `DEBUG` | 1/0 |
| `ALLOWED_HOSTS` | список хостов через запятую |
| `CSRF_TRUSTED_ORIGINS` | для CSRF при работе за прокси |
| `POSTGRES_DB/USER/PASSWORD/HOST/PORT` | подключение к БД |
| `TIME_ZONE` | таймзона Django |
| `PROMO_TIMEZONE` | таймзона границ акции |
| `PROMO_START_DATE` | начало акции, `YYYY-MM-DD` |
| `PROMO_END_DATE` | конец акции, `YYYY-MM-DD` |
| `PROMO_MIN_AMOUNT` | минимальная сумма чека |

Даты **обязательно** с ведущими нулями: `2026-01-01`, а не `2026-1-1`.

## Что реализовано

### Пользователи
- Стандартный `django.contrib.auth`.
- Регистрация и вход — дефолтные шаблоны Django.
- Модератор — пользователь с `is_staff=True`.
- Отдельный интерфейс модератора не нужен, используется админка.

### Модель чека
`lucky_receipt.models.Receipt`:
- ФН, ФД, ФП, дата и время покупки, сумма;
- статус: `pending` / `accepted` / `rejected` / `won`;
- причина отказа;
- пользователь, дата регистрации;
- `UniqueConstraint(fn, fd, fp)` — второй раз тот же чек не пройдёт.

### Регистрация чека
- Форма с серверной валидацией:
  - дата покупки входит в период акции;
  - сумма не меньше `PROMO_MIN_AMOUNT` (по умолчанию 1000 ₽);
  - ФН/ФД/ФП — только цифры, связка уникальна;
  - новый чек всегда получает статус «на проверке».
- Поле `qr_string` — необязательное. Если заполнено, строка вида
  `t=...&s=...&fn=...&i=...&fp=...` парсится:
  - **на клиенте** (JS) — автозаполнение полей сразу при вводе;
  - **на сервере** (`lucky_receipt.services.qr_parser`) — как fallback и на случай отключённого JS.
- Поле `photo` — необязательное. Загрузка фото чека с валидацией:
  - формат — JPEG, PNG или WEBP (проверка через Pillow, не только расширение);
  - размер — от 1 КБ до 5 МБ;
  - файл хранится как `ReceiptPhoto` с превью в ЛК и админке.

### Личный кабинет
- Список своих чеков: дата покупки, дата регистрации, сумма, статус, фото, причина отказа.
- Сортировка от новых к старым.
- Пагинация по 10.
- Кнопка «Зарегистрировать чек».
- Форма отправляется через `fetch`, ответ сервера отображается без перезагрузки.
- **Polling статусов**: страница раз в 15 секунд тихо проверяет через `/api/receipts/?ids=...`, не поменялся ли статус чеков. Если да —
  бейдж и причина отказа обновляются без перезагрузки. Опрос останавливается, когда вкладка в фоне.

### Админка
- Список чеков, фильтры по статусу и датам, поиск по ФН/ФД/ФП/пользователю.
- Карточка чека: смена статуса + обязательное поле причины при «Отклонён».
- Inline для фото чека с превью.
- Массовые действия:
  - «Принять выбранные чеки»;
  - «Вернуть на проверку»;
  - «Отклонить с причиной…» — промежуточная форма, одна причина на всю пачку;
  - «Отметить как победителя»;
  - «Экспортировать принятые чеки в CSV» (разделитель `;`, BOM для Excel).

### API
- `GET /api/receipts/` — чеки текущего пользователя в JSON.
- `GET /api/receipts/?ids=1,2,3` — только указанные чеки (в пределах
  `request.user`). Если `ids` есть, но не распарсились — пустой результат.
- Всегда фильтрует по `request.user` **первым делом**;
  чужие чеки отдать нельзя ни при каких параметрах.

### Инфраструктура
- `docker compose up --build` поднимает Postgres + Django.
- `docker/entrypoint.sh` ждёт готовности БД и накатывает миграции.
- `.env.example` с валидными значениями по умолчанию.
- Настройки логгирования через `LOGGING`.

## Спорные решения

**Уникальность чека по `(ФН, ФД, ФП)`.** Соответствует ТЗ и спецификации ФНС:
эта тройка — идентификатор фискального документа. Изменение любого поля
даёт «другой» чек формально. **Ограничение:** это не защищает от подбора
соседних значений (например, `i=12345` → `i=12346`) или генерации
правдоподобных троек скриптом. Проверка подлинности чека требует запроса
в API ФНС/ОФД, что выходит за рамки тестового и требует интеграции
с внешним сервисом. В реальной акции сюда добавляются:

- rate limit на регистрацию (например, не больше 10 чеков в час с одного аккаунта);
- суточная квота на пользователя;
- проверка чека в ОФД по QR;
- сигнал модератору, если с одного ФН приходит подозрительно много чеков.

**Повторная регистрация отклонённого чека.** Запрещена.
Связка `(fn, fd, fp)` уникальна для всех статусов. Причина: упрощает модель
данных, исключает подбор «переотправкой» и соответствует требованию ТЗ
«второй раз тот же чек не принимается».

**Границы периода акции.** Включительные: начало — 00:00:00,
конец — 23:59:59.999999. Трактуются в `PROMO_TIMEZONE` из `.env`,
а не в UTC. Это значит: если пользователь в другом часовом поясе,
«последний день акции» определяется по московскому (или указанному
в конфиге) времени.

**Часовой пояс в форме.** `datetime-local` отдаёт naive datetime.
Приводим к `PROMO_TIMEZONE` в `clean_purchased_at`. В БД всегда лежит
aware-время; `USE_TZ=True`.

**Информация модератора.** Поле `moderator_comment` доступно при любом статусе чека. Для «Отклонён» заполнение обязательно — иначе пользователю
непонятно, почему отклонили. Для «Принят» и «На проверке» комментарий
необязателен: модератор может оставить пояснение.

**API.** Принимает только `?ids=` для polling. Не принимает параметры
сортировки, фильтрации, `user_id`. Если бы понадобилось — добавляли бы
явный whitelist.

**QR-строка.** Поддерживаются форматы даты:
`%Y%m%dT%H%M%S`, `%Y%m%dT%H%M`, `%Y-%m-%dT%H:%M:%S`, `%Y-%m-%dT%H:%M`.
Если строка не парсится — форма возвращает понятную ошибку у поля
`qr_string`, а серверная валидация обязательных полей ловит остальное.
На клиенте QR парсится и подставляется в поля; если что-то не сработало
(битая строка) — сработает серверный парсер как fallback.

**Фото чека.** Необязательное поле. Проверка формата делается через
Pillow, а не только по расширению или `Content-Type` —
это отсекает переименованные PDF и пустышки. Максимум 5 МБ,
минимум 1 КБ. **Не делаем OCR** — распознавание ФН/ФД/ФП с фото
требует `tesseract`, даёт 60–70% точности на реальных фото и не
нужно, потому что есть QR.

**Клиентская валидация не заменяет серверную.** JS подсвечивает поля
и подсказывает, но окончательное решение — за `ReceiptForm.clean()`.
Отключение JS не ломает валидацию, только UX.

**Копейки.** Сумма — `DecimalField(decimal_places=2)`, на форме шаг
стрелок 1 ₽ (`step="1"`), ручной ввод `1500.50` допустим.
Минимум — 1000 ₽.

**Polling статусов.** Интервал 15 секунд, первый опрос через 3 секунды
после загрузки. Останавливается, когда вкладка скрыта
(`visibilitychange`), возобновляется при возврате. Каждый запрос
содержит cache-buster `&_=timestamp`. Логика «показанный статус
в `row.dataset.status`» — если сервер вернул то же значение, DOM
не трогаем.

## Что не сделано / план

Обязательная часть ТЗ закрыта. Из бонусов реализовано:

- ✅ строка из QR-кода с автозаполнением формы;
- ✅ загрузка фото чека с валидацией формата и размера;
- ✅ выгрузка принятых чеков в CSV из админки;
- ✅ автообновление статуса чека в ЛК без перезагрузки (polling);
- ✅ массовое отклонение с указанием причины из админки.

Не реализовано (осознанно отложено):

- **вёрстка под макет Figma** — структура и цвета  не сильно близко. Полноценная визуальная доработка — отдельный этап. Сейчас важнее было закрыть функциональность;
- rate limit и антифрод — описаны в «Спорных решениях»;
- проверка чека через API ФНС/ОФД — требует внешнего сервиса.

Что хотелось бы добавить при наличии времени:

- rate limit на регистрацию чека (защита от перебора);
- капча на регистрацию;
- уведомления пользователю при смене статуса его чека (email или in-app);
- Django REST Framework вместо ручного `JsonResponse` — если бы API рос;
- метрики/health-endpoint для деплоя (`/healthz/`).

## Работа с ИИ

При разработке использовался Claude как ассистент. Ниже честный разбор.

**Где помог сильнее всего.** Каркас проекта: настройка `docker-compose`, шаблон `Dockerfile` с ожиданием БД в `entrypoint.sh`,
скелет модели `Receipt` с `UniqueConstraint` и индексами. Отдельно —
валидация формы: генерация сообщений об ошибках, аккуратная работа
с `timezone.make_aware` и границами периода в `PROMO_TIMEZONE`.
Плюс шаблон README, структура тестов и код polling-скрипта
с учётом скрытой вкладки и дедупликации обновлений.

**Что выдал неправильно и как это заметил.**

  Поймал по трейсбеку `ModuleNotFoundError`.
- В `_validate_digits` тип аргумента был `str`, хотя `cleaned_data.get()` возвращает `str | None`. Pyright это подсветил.
- Значения по умолчанию в `.env.example` были с пустыми `POSTGRES_*`. Проверил на чистом `cp .env.example .env` — упало на подключении к БД.
- Даты в примере оказались из 2025 года при текущем 2026 — тоже заметил при ручном прогоне.
- Тест `test_export_accepted_csv` проверял `assert "20" not in body`, где `"20"` встречается внутри года `2026`. Ложное срабатывание нашёл, когда прогнал `pytest`.
- QR-поле: серверная логика автозаполнения была, но JS-валидация
  блокировала отправку раньше, чем запрос уходил на сервер. Обнаружил при ручной проверке в браузере.
- В фабрике тестовых изображений сплошной цвет сжимался до 1.5 КБ, что не проходило порог валидатора в 10 КБ. Заменил на шум через `os.urandom` и снизил порог до 1 КБ — так и реалистичнее, и устойчивее к реальным маленьким картинкам.
- Polling: первый вариант `list.js` жёстко искал бейдж по `[data-cell="status"] .badge` и молча не находил его, если в HTML-разметке что-то отличалось. Переписал на каскад селекторов и добавил debug-логи, которые помогли быстро найти проблему.

**Что бы переписал, будь больше времени.**

- Вынести общую логику валидации реквизитов (`fn`/`fd`/`fp` — только
  цифры) в отдельные валидаторы Django, чтобы не дублировать между формой и моделью.
- Покрыть `admin.py` более детальными тестами — сейчас проверяются только два сценария из четырёх действий.
- Добавить `pytest.mark.django_db` там, где это уместнее, чем `TestCase`.
- доработать фронтенд, "причисать код".
